# 核心概念与术语详解

## 1. 什么是"数据湖"（Data Lake）？

数据湖是一个以**原始格式**存储海量数据的集中式存储库。它的核心设计哲学是 **"读时模式（Schema-on-Read）"**：

- **写时模式（Schema-on-Write）**：传统数仓在数据写入前，必须先定义好表结构（字段、类型），数据要先"整形"才能入库。
- **读时模式（Schema-on-Read）**：数据写入时不要求预先定义结构，原样（Raw）存进去，直到读取分析时才套用结构。

这种哲学带来**极高的灵活性**：同一份原始数据可以被 BI 报表、数据科学、机器学习等多种下游应用以不同方式解读，互不干扰。

> 灵活性也有代价：没有元数据和治理的数据湖会迅速退化成"数据沼泽（Data Swamp）"——一大堆文件，谁也不知道里面是什么。所以后面会讲到，**元数据（Catalog）是数据湖的灵魂**。

## 2. 关键术语解释

### 2.1 元数据（Metadata）

**描述数据的数据**。在数据湖中，元数据记录数据的"位置、格式、类型、创建时间、所有者"等信息。

> 打个比方：元数据就是图书馆的书目卡片。没有卡片，书架上就是一堆无法检索的书；没有元数据，数据湖就是一堆无意义的文件。

### 2.2 Catalog（数据目录）

元数据管理的**顶层逻辑实体**，相当于"图书馆的总索引"，用于不同业务或不同用户之间的元数据隔离与权限管控。

- 一个 Catalog 下可以包含多个 Database。
- 例如：建一个 `prod_catalog`（生产目录）和一个 `test_catalog`（测试目录），互不影响。

### 2.3 Database（数据库）

Catalog 下的**二级逻辑单元**，用于组织数据表，功能类似传统关系型数据库中的"数据库（Schema）"。

### 2.4 Table（数据表）

实际存储数据元信息的最小单元，定义了数据的 Schema（字段、类型等）和物理存储位置。

> 注意：数据湖里的"表"是**逻辑概念**。它的"内容"其实是 OSS/HDFS 上的一堆文件，Table 只是用元数据把这些文件"组织"起来。

### 2.5 ACID 事务

指**原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）**四个特性。

- 传统的非事务性数据湖（仅使用 Parquet/ORC 文件）**无法保证**并发写入时的一致性和更新操作的完整性。
- 因此现代企业级数据湖**必须**采用支持 ACID 的表格式：**Delta Lake、Apache Iceberg、Apache Hudi**。
- 有了 ACID 表格式，才能在数据湖上进行 **Upsert/Delete（更新/删除）** 和 **Schema Evolution（结构演变）**。

### 2.6 Schema Evolution（结构演变）

指数据表的结构（新增、删除、修改字段）可以随时间演进、且**不破坏既有数据**的能力，是保证数据湖长期可扩展的核心功能。

> 场景：源库 SQL Server 的订单表新增了 `discount_amount` 字段。开启 Schema Evolution 后，入湖任务不会因结构变化而中断，新字段自动追加到湖表中。

### 2.7 分区（Partitioning）

一种物理数据组织技术，把大表的数据按一个或多个列（如日期、区域）切分成更小、独立的子目录存储。

- 好处：查询时无需扫描全表，只读相关分区，极大提升效率。
- 例如按 `dt`（日期）分区后，查"昨天"的数据只需读 `dt=2026-09-07/` 一个目录。

### 2.8 分桶（Bucketing）

另一种数据组织技术，按某列的哈希值把数据分到固定数量的"桶"里，适合**基数过高**的字段（如用户 ID）。

## 3. 数据湖 vs 数据仓库 vs 湖仓一体

| 概念 | 特点 | 典型场景 |
| :--- | :--- | :--- |
| 数据湖 | 读时模式，存原始数据，灵活 | 机器学习、探索分析 |
| 数据仓库 | 写时模式，存结构化数据，性能高 | BI 报表、固定指标 |
| 湖仓一体（Lakehouse） | 数据湖 + ACID 表格式（Delta/Iceberg/Hudi） | 两者兼得，现代主流 |

> 本系列文档讲的"数据湖"，默认就是**湖仓一体**形态（使用 Delta Lake / Iceberg 这类 ACID 表格式）。
