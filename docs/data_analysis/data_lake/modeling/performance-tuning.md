# 通用性能与扩展性设计

## 1. 小文件是头号杀手

**问题**：小文件（< 128MB）会让查询产生大量元数据开销和任务调度开销，严重拖慢性能。

**来源**：流式或频繁微批写入（如 DTS 每次同步都新写一批小文件）。

**对策**：定期执行合并命令——

- Delta Lake：`OPTIMIZE 表名`
- Iceberg：`COMPACTION`

```sql
OPTIMIZE ods_sqlserver_db.orders;
```

## 2. 分区策略

- **原则**：选基数适中、查询常用的字段做分区，最常用的是日期（`dt`）、区域。
- **误区**：不要选基数过高的字段（如订单 ID），否则会产生海量小分区。
- **高基数字段**：更适合用**分桶（Bucketing）**。

## 3. 文件格式与压缩

- 列式格式（Parquet / ORC）对分析型查询友好。
- 可选压缩（Snappy / Zstd）在存储与 CPU 之间平衡。

## 4. 生命周期管理

- 对历史分区设置**生命周期规则**：如 Bronze 30 天后转低频存储、1 年后删除，控制成本。
- 在阿里云中通过 **DLF 湖管理** 或 **OSS 生命周期** 配置。
